# Application threat and control matrix

## Scope and trust boundaries

Checked-in App Router pages consume fixture data via `lib/directory.ts`. The browser and URL parser are untrusted. Build dependencies, checked-in CSS, runner and registry are a separate trust boundary. The local moderation and advertising programs can mutate per-instance memory. Public route imports do not connect to those programs. Production would add identity, private data, cache, staff and vendor boundaries that do not exist in the demo.

| Surface | Evidence and uncertainty | Release concern |
| --- | --- | --- |
| Search and URL handling | The route normalizes repeated values and rejects malformed text. Category selection uses the known category allowlist. Profile lookup requires exact city and listing association. React rendering uses text and recognized URL state. Read the [execution ledger](evidence.md) for sampled assertions. | Add request-size and rate bounds, cache key and URL log/referrer review. Current normalization alone is not an abuse limit. |
| City isolation and ordering | Fixed public fixtures, city-dependent lookup, explicit category filter. Existing production HTTP suite checks 12 cross-city profile 404s. Additional checks compare ordered rendered titles for each city with and without filters. | Future server authorization, database scope, cache keys, exports and background jobs must enforce isolation independently. |
| SSRF, redirects and content sinks | No app-level outbound fetch or redirects were found in the scoped app/components/lib review. No raw-HTML injection sink was found in the public app. Public links use fixture IDs and URLSearchParams. Framework-managed assets and the image optimizer are a separate surface. | Re-review optimizer default policy, redirects, egress and all future destinations. No SSRF exploitability ruling, redirect fuzzing, external scanning, or media fetch test. |
| Headers and cache | Loopback observations in the [ledger](evidence.md) concern a plaintext local process. Noindex was verified as crawler guidance only. | Design and test HTTPS, framing/CSP, referrer policy, content type, route-specific cache policy, and information minimization in the approved release environment. Don't infer edge posture from loopback. |
| Error and resource boundaries | Custom not-found and city error boundary exist. The HTTP suite checks invalid and malformed paths. Successful isolated requests give no concurrency, saturation or error disclosure guarantee. | Fault injection and disclosure review under written authorization, plus workload limits, safe error messages and incident response before launch. |
| Advertising eligibility and segregation | Phase 5 placement registry checks city/category/slot and simulated windows. Creative decisions are reason-coded and do not auto-schedule. In-memory revisions, request replay and collision checks are unit-tested. No public app imports the simulator. Nine ad/admin URLs return 404 in the named probe set. | Records are local and ephemeral and have no durable audit, actor authorization or delivery controls. Separate ownership/approval gates and production log/audit review would be necessary before considering activation. |

The [Phase 5 ADR](../../adr/0003-offline-advertising-simulation.md) describes simulated approval and allocation. Public organic sorting and the original `Sponsored — example only` disclosure are independent of those outcomes. The offline `Sponsored — simulation only` label is not present on the tested public Dubai page. No live ad serving, reporting, billing or tracking is assessed or enabled.
