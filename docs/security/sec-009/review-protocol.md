# Independent review protocol

## Intake and independence

The product owner must separately authorize the exact candidate, allowed work, evidence handling, deliverables, stop authority and any engagement terms before assigning a reviewer. Require demonstrable experience reviewing identity and multi-tenant authorization, transactional failure/recovery and audit integrity. Require disclosure of authorship, reporting lines, financial/vendor ties and previous consulting. Disqualify people who designed or implemented the candidate, depend on its acceptance, or cannot report adverse findings directly to the owner. Seek relevant specialist support if expertise is missing. Privacy and qualified UAE, Oman and Qatar counsel own their respective determinations.

Record candidate and merge-base SHAs, lockfile digest, named reviewer, qualifications and conflicts, date, environment, permissions, allowed evidence and storage, prohibited surfaces, and scope/termination approvals. Restrict this reproduction to an offline synthetic test environment and loopback. The package includes a dated dependency registry result for provenance. Fresh registry access requires explicit permission within the review scope. Stop for credentials, real data, unsupported tooling, external target testing, new infrastructure, evidence exposure or missing authorization.

## Coverage and reproducibility

1. Check the manifest and compare the exact candidate with the baseline. Match CI run, attempt, head SHA, artifact digest, retention expiry and individual step outcomes. If retained evidence is unavailable, record the gap and rerun where authorized.
2. Record Node/npm versions, OS/architecture, checkout and clean lockfile installation (`npm ci --no-audit --no-fund`), including whether a trusted local cache was used. Run `npm test`, `npm run typecheck` and `npm run build`. Capture exit codes, totals, durations and unexpected warnings.
3. Review SEC-003 artifact files and decision policy. With permitted registry access, run collect/evaluate per the [SEC-003 controls](../SEC-003-ci-controls.md) and record the UTC timestamp and lockfile digest. Distinguish a clean advisory snapshot from run failure or missing evidence.
4. Start the production build on `127.0.0.1:43138`. Run `node tests/profile-http.mjs http://127.0.0.1:43138`. Capture six fictional profiles, city/filter and organic order, noindex, sponsor disclosure and nine admin/moderation/advertising 404s. Stop the process afterward.
5. Compare [all 16 assessment rows](invariant-assessment.md) to the exact test code. Challenge A7-01–06 on trust sources, freshness, city/object scope, conflict history and worker/egress authority. Challenge T7-01–06 on version binding, revocation/commit ordering, replay semantics, failure cuts, stale visibility and restore. Challenge P7-01–04 on minimized events, privileged custody, market-specific flows and lifecycle enforcement. For each, record whether support is proposed, verified offline, unimplemented or requires further independent evidence.
6. Trace attacker and operator access at ingress, session, writer, repository, worker/cache, custody/backup and market boundaries. Record prerequisites, assets, expected denied effects, observable results, uncertainty and residual impact. Rerun bounded synthetic cases independently and link output to the evidence row. Send changes and new test scope back to the owner.

The final written disposition must give evidence references, reproducibility results, findings by requirement and severity, remediation and retest criteria, unresolved or out-of-scope items, expiry and reopening triggers. Use the [blank handoff](independent-review-handoff.md). The later production G2 assessment requires its own authorization and candidate-specific evidence.
