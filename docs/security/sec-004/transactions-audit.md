# Transaction, audit custody and recovery

Status: DESIGN. The local Phase 4 and 5 simulations use process-local snapshots. They do not provide the transaction isolation, identity or retention described here.

## Command and invariant contract

A command envelopes a schema version, registered action, city and stable resource identifiers, expected resource revision, allowlisted reason code where relevant, action-specific typed fields, and a bounded idempotency key. Bind the caller to server-derived principal, current session assurance and city grant/grant revision; do not consume corresponding authority from command fields. Assign correlation ID and timestamps at the server. Reject unsupported versions and fields, malformed IDs, unbounded text, state shortcuts and unknown reasons. Store any approved narrative separately after classification/redaction. Do not retain raw input in audit or idempotency logs.

| Example command | Guard or invariant |
| --- | --- |
| Owner submits | Current ownership, city match and draft revision required. Snapshot exact version submitted for review. |
| Moderator starts/decides | Valid current reviewer and grant, permitted state, allowed reason, conflict-of-interest check, exact submitted version and any applicable evidence. Rejected work requires a fresh version and review. |
| Separate verification | Own scoped check and decision expiry. Never infer verification from editorial approval. |
| Administrator publishes | Recorded approval and any required verification match exact content/policy versions; callable only by a distinct eligible principal. Approved and verified do not imply published. |
| Withdrawal, transfer or emergency hold | Revoke visibility or invalidate stale evidence and schedule authorized purge. Transfer cannot implicitly reactivate an object or grant authority to its previous owner. |
| Advertiser review / approval | Future only. Match city/category/creative/destination rights, distinct approval, exact version, no automatic scheduling or delivery. Organic ranking remains independent. |

## Ordering, freshness and idempotency

1. Validate request and resolve a city-scoped object. Authenticate and authorize before admitting it or revealing a receipt. Take the canonical request fingerprint over version, scoped object, action, expected revision and validated semantic payload, with deterministic typed serialization. Bind the receipt key to principal, city, action, object and client idempotency key, never to a client role.
2. Begin one transactional consistency boundary for current authority, state, audit event, receipt and outbox. Fence against authoritative session/account/grant/policy versions and current ownership. Revocation and grant changes participate in the same transaction ordering or an independently reviewed equivalent version fence, so a revocation committed before the command cannot be bypassed. A cached claim or remote permit without a freshness/commit fence is insufficient. Enforce serializable behavior or equivalent locked invariants with tested isolation. Establish ordering of grant/policy and tenant/object locks, then receipt uniqueness, acquired deterministically by canonical immutable IDs across multi-record commands. Retest deadlocks and serialization conflicts; retries use bounded backoff and re-authorize.
3. Under that boundary, check the scoped receipt with a unique constraint. Same fingerprint with current authority returns the original minimal outcome without writing again. Different fingerprint on the same key conflicts. Replay after authority is lost denies even if a receipt exists. A new key still requires the expected current revision and a legal transition. Use server time and versioning. Competing commands must have at most one winning mutation for a given revision.
4. Atomically commit affected state, a single append-only event, receipt, and durable logical outbox entry. An event/receipt write error aborts everything. Publish nothing before commit. Return only a minimal result after commit; if the response is lost, an authorized retry recovers the stored outcome.
5. Deliver authorized projections from the outbox after commit with deduplication by event ID and ordered resource revisions. Require workers to verify service scope and, for actor-dependent work, current delegated grant. Keep queues tenant-scoped. Drop stale versions, quarantine inconsistent messages and reconcile before visibility changes. Delivery is at least once; dedupe covers receiver side effects. Use a visibility gate or expiry bound to stop serving revoked content during purge backlog.

Receipt TTL and key reuse behavior require policy approval. Proposed behavior is to preserve collision protection for the entire retry horizon and reject superseded commands by revision afterward. Use structured failure classes (unauthenticated, scope-denied, invalid, conflict, unavailable), redact response detail, and avoid telling an unauthorized caller which private records exist.

## Durable audit and custody

- Authoritative event includes event ID, schema and policy version, server UTC time, scoped correlation ID, pseudonymous principal and effective role, city, action and target type/ID, outcome reason code, previous/resulting revision and references to related decisions. No credentials, session tokens, contact details, full media URLs, queries or free-text evidence. Keep denial/security events in a separately governed stream. Avoid exposing global sequence gaps across cities.
- Application writer may append narrowly scoped records and may not rewrite or delete history. Readers need case-specific grants and redaction. Use isolated custody with distinct administrators, append-only storage and time-bounded retention controls. Any expiry, redaction or legal hold requires authorized policy and a traceable decision. Separate identifying mappings and content; seal minimum metadata and allow lawful expiry or removal through policy without rewriting ordinary event history.
- Integrity monitoring compares transactional and custody streams by event ID, revision and counts; durable signed manifests or integrity checkpoints can help detect tampering but do not prove immutability or independence. Separately control signing keys, rotations and revocation; use independent verification and split duties for audit access, export, retention, hold and key changes. Log and inspect custody/admin access as well as business actions.
- Restore state, receipts, audit and outbox at a consistent checkpoint, replay idempotently and reconcile before releasing writes/projections. Test failures before commit, after commit before acknowledgement, during re-delivery and during custody lag. Recover stale leases, reauthorize queued work, check quarantine and sign off on discrepancies. Do not backfill a missing event with invented historic identity or timestamp; record provenance and independently approved corrective entries.

Stop new privileged writes when required transactional auditing is unavailable, custody lag breaches the approved bound, or integrity/recovery cannot be verified. Any independent audit store and backup location remains conditional on counsel, owner and custody approval.
